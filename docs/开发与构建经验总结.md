# Sandboxie-Plus 本地化改造：编译、踩坑与实现全过程

> 本文记录一次对 **Sandboxie-Plus v1.19.1** 的本地化改造：从零搭起能编译内核驱动 + Qt UI 的构建环境，改驱动解除付费授权门禁，重写快照恢复逻辑，把 MCP/CLI 换成 Rust 本地实现，并在 SandMan 原生菜单里加上「导入文件夹 / 导入程序 / 运行指定程序…」。
>
> 所有结论都来自本机实际编译、实机运行与故障复现，不是照抄官方文档。**仅供个人自用与学习，非官方发布。**
>
> 环境：Windows 11 x64（THUNDEROBOT R16，GPT/UEFI，Secure Boot 已关闭）；VS 2022 **Build Tools** 17.14（只有 v143 工具集，**没有装 WDK MSI、没有 ATL/MFC**）；Qt 6.8.4（xanasoft 定制 msvc2022_64 包，免安装解压）；Rust 1.96；当前 shell 非管理员（UAC 提示被禁用，装驱动这类操作只能交给用户手动执行）。

## 1. 构建环境：没有 WDK MSI、没有 ATL 怎么编

### 1.1 三件套各自从哪来

- **MSVC**：VS 2022 Build Tools，`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\cl.exe`。
- **Qt 6.8.4**：官方 `Installer/buildVariables.cmd` 里写的是 `qt_version=6.8.4`，用的是 xanasoft 定制包
  `https://github.com/xanasoft/qt-builds/releases/download/v6.8.4-ssl-lgpl/qt-everywhere-6.8.4-Windows_7-MSVC2022-x86_64-release.7z`（约 150MB），
  解压即用，`qmake -v` 正常。**包里没有 jom**，所以只能用 `nmake`。
- **WDK 内核头/库**：不装 MSI（要管理员 + 装完还可能有别的麻烦），改从 nuget 下
  `https://api.nuget.org/v3-flatcontainer/microsoft.windows.wdk.x64/10.0.26100.6584/microsoft.windows.wdk.x64.10.0.26100.6584.nupkg`（约 110MB），
  解压后把 `c\` 当作 `WDKContentRoot`，里面有 `include\10.0.26100.0\{km,shared,um,wdf}`、`lib\10.0.26100.0\km\{x64}`、`build\10.0.26100.0\WindowsDriver.*.props`。
- **Windows SDK**：Build Tools 自带 `C:\Program Files (x86)\Windows Kits\10\`（提供 `shared\warning.h`、`um`、`ucrt`）。**这一步很关键**，见 2.4。

> 结论：**驱动不必重编整个内核栈，也不需要 WDK 的 MSBuild 工具集** —— 用 nuget 的头/库 + 手写 `cl /link` 完全够，绕开了「本机 BuildTools 的 PlatformToolsets 里没有 `WindowsKernelModeDriver10.0`」这个死路。

### 1.2 为什么不用 msbuild 编驱动

`Sandboxie/core/drv/SboxDrv.vcxproj` 的配置是 `PlatformToolset=WindowsKernelModeDriver10.0`，而 BuildTools 的
`MSBuild\Microsoft\VC\v170\Platforms\x64\PlatformToolsets\` 只有 `v143`；nuget WDK 包里也**不含** PlatformToolsets。
硬造一个假 toolset 目录去导入 WDK props 也能成，但更直接的路是手写编译命令行（见 `build-scripts/build_drv.cmd`）。

### 1.3 用户态（SandMan）的编译顺序

顶层 `SandboxiePlus.pro` 的 `SUBDIRS` 顺序**不满足链接依赖**（SandMan 排在 QSbieAPI 前面），直接 `nmake` 会出现
`LINK : fatal error LNK1181: 无法打开输入文件"QSbieAPI.lib"`。两个可选做法：

- 一直用 `qmake ... -r` + `nmake`（qmake 版会重排/补齐），或
- 按依赖顺序逐个 `nmake -f Makefile.<proj>.Release`：`MiscHelpers` → `QSbieAPI` → `qtsingleapp` → `UGlobalHotkey` → `SandMan` → `SbieMcp`。

另有三个独立的坑：

1. **`qtsingleapp.lib` 落在多层目录**：`QtSingleApp/qtsingleapp/Bin/x64/Release`，需要手动拷到 `SandboxiePlus/Bin/x64/Release/`。
2. **`UGlobalHotkey` 不在 SUBDIRS 里**：得单独 `set build_arch=x64` + `qmake uglobalhotkey.qc.pro ... -o Makefile.ugh` + `nmake -f Makefile.ugh`。
3. **改完 `.pro` 必须重跑 qmake**：只 `nmake` 不会重新生成 Makefile，改的 `LIBS` 不生效（这个坑让我们白等了一轮构建）。

## 2. Qt 侧编译：四个「官方能编、本机编不了」的问题

### 2.1 `Unknown module(s) in QT: winextras`

`SandMan/SandMan.qc.pro` 有两处 `QT += winextras`（Qt5 遗留）。Qt6 没有这个模块 → 注释掉。
代码里唯一用到的是 `WinHelper.cpp` 的 `QtWin::fromHICON(icon)`，Qt6 分支已有 `QImage::fromHICON`，但 **Qt6 也没有这个 API**（Qt5 有）。

### 2.2 自己实现 `QImage ImageFromHICON(HICON)`

`QImage::fromHICON` 在 Qt6 被移除。自实现的要点：

1. `GetIconInfo()` 拿 `hbmColor` / `hbmMask`；
2. `CreateDIBSection` 建 32bpp **自顶向下** DIB（负 `biHeight`）；
3. `DrawIconEx(..., DI_NORMAL)` 画进去；
4. **修 alpha**：很多图标的 32bpp 位图 alpha 全 0，需要「alpha 全零则按 mask/亮度补不透明」，否则整张图透明。

### 2.3 `atlbase.h` 找不到（BuildTools 不带 ATL）

`Views/FileView.cpp` 用了 `CComPtr` / `CComHeapPtr`。本机 `...\14.44.35207\atlmfc\include\atlbase.h` 不存在。
写了 `SandMan/Helpers/AtlShim.h` 提供最小实现：

- `CComPtr<T>`：`AddRef/Release/Attach/Detach/operator T*/operator->/operator&/operator!/赋值`，以及 `CoCreateInstance` / `QueryInterface` 便捷；
- `CComHeapPtr<T>`：析构 `CoTaskMemFree`，`operator&` / `operator->`。

同时把 `IID_PPV_ARGS(&item)` 这类宏改成 `__uuidof(IShellItem), (void**)&item`（宏本身来自 ATL 头）。

### 2.4 `try/__except` 宏只存在于 SDK 的 `shared\warning.h`

驱动里 `ipc_port.c` 用的是 `try { ... } __except(...)`（小写），这些是宏：

```c
/* C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\shared\warning.h */
#define try    __try
#define except __except
#define leave  __leave
```

而 **nuget WDK 包的 `include\...\shared\` 里没有 `warning.h`**（也没有完整的 `ntdef.h`）。
所以即便把 SDK 的 `shared` 加进 `INCLUDE` 也不够（`ntdef.h` 走的是 WDK km 侧，不会去 include `warning.h`）。

**解法**：编译驱动时对**所有文件**强制包含它 ——

```
cl ... /FI"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\shared\warning.h"
```

编译报错长得很有误导性：`error C2065: "try": 未声明的标识符`、`error C2706: 没有匹配 __try 的非法 __except`、`error C2703: 非法的 __leave 语句`。

### 2.5 `resource.rc` 依赖 `afxres.h`

无 ATL/MFC 时提供垫片 `drvshim/afxres.h`，内容只需 `#include <winres.h>` + `#include <winver.h>`。

## 3. 驱动编译：四个必须知道的硬约束

### 3.1 不能按 ClCompile 全量编

`.vcxproj` 里列了 63 个 `.c`，但大量文件带 `ExcludedFromBuild` 条件（按 `SbieRelease|x64` / Win32 / ARM64 区分）。
**x64 实际只有 36 个**。全量编会一次性炸 22 个文件，看起来像"环境坏了"，其实只是编了不该编的。

用 `build-scripts/drv_list.py`（`xml.etree` 解析 vcxproj，按条件求值）输出真正要编的清单，别手抄。

### 3.2 汇编只编 `util_asm.asm`

`aulldvrm.asm` 在 `SbieRelease|x64` 是 `ExcludedFromBuild=true`。命令：`ml64 -c -Cx -nologo -D_WIN64 -Zi -Fo<obj> util_asm.asm`。

### 3.3 msgs 头文件的生成链（parse.exe → mc）

驱动 include `msgs\SbieRelease\msgs.h`，这个头不是仓库里现成的，要两步生成：

1. `msgs/parse.c` 编译成 `parse.exe`，遍历 `Text-*.txt` 生成 `msgs.mc`；
2. `mc /h SbieRelease /r SbieRelease -u msgs.mc` → `msgs.h`。

三个连环坑：

- `parse.c` 要 `/I ..`（`..` 是 Sandboxie 根，`common/list.h` 在那），**但不要把 `common/list.c` 一起编**，否则 `LNK2005: List_Insert_After 已经在 parse.obj 中定义`（`parse.c` 自带 list 实现）。
- 若不加特殊宏，`parse.exe` 跑完**不生成 `msgs.mc`**，而是生成两个名为 `S` 和 `m` 的垃圾文件。
  原因：`swprintf` 在 UCRT 下是**宽字符**语义，而源码按窄字符用（伴随 C4047/C4024 告警），导致 `CreateFile(L"msgs.mc")` 之类被拼成乱码文件名。
  **解**：编 `parse.exe` 时加 `/D_CRT_NON_CONFORMING_SWPRINTFS` **且** `/DUNICODE /D_UNICODE`。
- 先有 `msgs.mc` 才能 `mc`，否则报 `mc : error : errno 2 trying to open file <msgs.mc>`。

### 3.4 链接要补 `BufferOverflowFastFailK.lib`

驱动开了 `/GS-`，但上游代码引用了 `__fastfail` 等符号 → 链接时从 WDK `lib\10.0.26100.0\km\x64\` 补这个 lib。
最终链接参数（`build_drv.cmd`）：

```
link /DRIVER /SUBSYSTEM:NATIVE /ENTRY:DriverEntry /INTEGRITYCHECK /OUT:SbieDrv.sys ^
     <36 个 obj> util_asm.obj resource.res ^
     ntoskrnl.lib hal.lib wmilib.lib fltmgr.lib Ksecdd.lib Fwpkclnt.lib ntstrsafe.lib BufferOverflowFastFailK.lib
```

编译开关：`/c /GS- /GR- /EHs-c- /W3 /kernel /D_WIN64 /D_AMD64_ /DPOOL_NX_OPTIN=1 /DWIN9X_COMPAT_SPINLOCK /DUNICODE /D_UNICODE /DDEPRECATE_DDK_FUNCTIONS=1 /DMSC_NOOPT`。

## 4. 授权门禁：它到底在哪、为什么改 UI 没用

### 4.1 三条链路

1. **驱动侧算 feature flags**：`Sandboxie/core/drv/api.c:1235 Api_QueryDriverInfo` 按 `Verify_CertInfo` 组装 `SBIE_FEATURE_FLAG_*`，SandMan 拿它决定图标/功能可用性。
2. **驱动侧杀进程（硬拦截）**：`Sandboxie/core/drv/process.c:839`

```c
if (!(Verify_CertInfo.active && Verify_CertInfo.opt_sec) && !proc->image_sbie) {
    /* 按 use_security_mode / SysCallLockDown / RestrictDevices / UseRuleSpecificity /
       UsePrivacyMode / bAppCompartment(NoSecurityIsolation) / ProtectHostImages
       挑出 exclusive_setting，非空才报 MSG_6004 并 5 分钟后杀掉 */
    Process_ScheduleKill(proc, 5*60*1000);
}
```

3. **`Verify_CertInfo` 由验签决定**：`Sandboxie/core/drv/verify.c` 用 `KphVerifySignature()` + 硬编码公钥校验官方证书。
   **私钥在厂商手里，改不出来** —— 所以只能改「验签结果的收口处」。

### 4.2 正确的单点改法

`verify.c` 的 `KphValidateCertificate()` 所有失败路径最终都 `goto CleanupExit;`，因此在 `CleanupExit:` 之后、打印调试信息之前插入：

```c
Verify_CertInfo.State = 0;
Verify_CertInfo.active = 1;
Verify_CertInfo.expired = 0;
Verify_CertInfo.outdated = 0;
Verify_CertInfo.grace_period = 0;
Verify_CertInfo.locked = 0;
Verify_CertInfo.lock_req = 0;
Verify_CertInfo.opt_desk = Verify_CertInfo.opt_net = 1;
Verify_CertInfo.opt_enc = Verify_CertInfo.opt_sec = 1;
Verify_CertInfo.type = eCertEternal;
Verify_CertInfo.level = eCertMaxLevel;
Verify_CertInfo.expirers_in_sec = 0;
Verify_CertInfo.status = STATUS_SUCCESS;
```

一处改动同时覆盖「无证书 / 验签失败 / 过期 / outdated / grace period」全部情形，`process.c` 那两个条件自然通过。
字段定义见 `Sandboxie/core/drv/verify.h:23-47`（`SCertInfo` 是 union，`expirers_in_sec` 在 `:47`）。

### 4.3 还有一道「调用方签名」门禁

`Sandman.exe` 自己启动时会被驱动查签名：`api.c:966`

```c
if (NT_SUCCESS(status) && !MyIsCallerSigned()) status = STATUS_INVALID_SIGNATURE;
```

`MyIsCallerSigned()`（`util.c:528`）原本只在 **testsigning 已开启**或**调用方有厂商签名**时返回 TRUE，否则 SandMan 弹
「Sandboxie-Plus Manager (SandMan.exe) does not have a valid signature (SandMan.exe.sig)」。
**只靠 testsigning 不是好办法**（用户以后一关测试模式就复发），所以直接把它改成无条件放行：

```c
_FX BOOLEAN MyIsCallerSigned(void)
{
    UNREFERENCED_PARAMETER(status);
    return TRUE;   /* LOCAL BUILD: accept every caller */
}
```

> 附带发现：`Sandboxie/core/svc/ProcessServer.cpp:1547 PipeServer::IsCallerSigned()` 是另一套，只挡 updater，与本问题无关。

## 5. 签名与安装：自签 PKI 的正确姿势

### 5.1 单层自签为什么不行

`New-SelfSignedCertificate -Type CodeSigningCert` 签出来是 **终端实体（BasicConstraints: CA=false）**，`signtool verify /pa` 报
`A certificate chain processed, but terminated in a root certificate which is not trusted`；
强行给终端证书加 `CA=true` 又报 `A certificate's basic constraint extension has not been observed`（非 critical 标记问题）。

**必须两级**：

```powershell
# 根（CA=true 要用 critical 标记）
$root = New-SelfSignedCertificate -Subject 'CN=Sandboxie Local Root CA, O=Sandboxie Local Build, C=CN' `
  -Type Custom -KeyUsage CertSign,CRLSign,DigitalSignature -KeyUsageProperty Sign `
  -KeyExportPolicy Exportable -KeyAlgorithm RSA -KeyLength 4096 -HashAlgorithm SHA256 `
  -NotAfter (Get-Date).AddYears(20) -CertStoreLocation 'Cert:\CurrentUser\My' `
  -TextExtension @('2.5.29.19={critical}{text}CA=true','2.5.29.37={text}1.3.6.1.5.5.7.3.3')

# 叶（代码签名）
$leaf = New-SelfSignedCertificate -Subject 'CN=Sandboxie Local Code Signing, O=Sandboxie Local Build, C=CN' `
  -Signer $root -Type CodeSigningCert -KeyExportPolicy Exportable `
  -KeyAlgorithm RSA -KeyLength 4096 -HashAlgorithm SHA256 `
  -NotAfter (Get-Date).AddYears(20) -CertStoreLocation 'Cert:\CurrentUser\My'
```

签名时**必须显式指定叶证书、并把根带进签名块**（PFX 里有多张证书，不指定会挑错）：

```
signtool sign /v /fd sha256 /sha1 <leaf-thumbprint> /f leaf.pfx /p <pwd> /ac root.cer <file>
```

> 必须在 **PowerShell 7** 下生成证书：Windows PowerShell 5.1 缺 `RSACng` 类型（类型名是 `[System.Security.Cryptography.RSACng]`，不在 `X509Certificates` 命名空间下）。

### 5.2 testsigning 与「重启才生效」

- 自签驱动要加载，需要 `bcdedit /set {current} testsigning on`（BCD 启动项，**必须重启**），且 Secure Boot 关闭。
- `signtool verify /kp`（内核策略）对自签**必然**报 `Signing Cert does not chain to a Microsoft Root Cert` —— 这不是错，testsigning 下只要求链到受信任根。
- **驱动的实际路径不在 `System32\drivers`**：服务 `BINARY_PATH_NAME = \??\C:\Program Files\Sandboxie-Plus\SbieDrv.sys`。替换文件只需动 Program Files 下的那份。

### 5.3 驱动正在被内核占用时怎么换文件

停服务也删不掉（映射中）。用 `PendingFileRenameOperations` 让系统在下次启动时换：

```powershell
# HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\PendingFileRenameOperations (REG_MULTI_SZ)
\??\C:\Program Files\Sandboxie-Plus\SbieDrv.sys            ->  (空)    # 先删
\??\C:\Program Files\Sandboxie-Plus\SbieDrv.sys.localnew   ->  \??\...\SbieDrv.sys  # 再改名
```

脚本里要做**幂等**（第二次运行不重复追加），并在写入后 `bcdedit /enum {current}` **回读校验** testsigning 真的为 Yes。

### 5.4 UI 只有两个文件在变时，别让用户重启

SandMan/QSbieAPI 替换后只要重启 SandMan 进程即可（`update-ui.ps1`）。**驱动换了才需要重启系统。**

## 6. 快照恢复：`runtime_boot_failed` 的真正成因

### 6.1 SandMan 的快照到底做了什么

- `TakeSnapshot`：把箱根的 `drive/`、`user/`、`share/` **整个 move** 进 `snapshot-N`（只有 `RegHive` 是复制）。
  于是快照成链后，子快照只存**变化**，父层是只读下层。
- `SelectSnapshot`（原版）：复制 `RegHive` → `CleanBoxFolders()` 清空 `drive/user/share` → 一个文件都不铺回，指望驱动把 `snapshot-N` 当只读下层合并。

结果：合并视图里**能看到** `...\accounts\<hash>\runtime\artifacts`，但一旦 `chmod`/创建就 `ENOENT`（下层只读，上层没有实体）——
Electron 应用启动时正好要 `chmod` 这个目录，于是报 `runtime_boot_failed`。

### 6.2 修法：全量物化（materialize）

`CSandBox::SelectSnapshot` 重写为：

1. 按 `Snapshot_N/Parent` 回溯出 `root → 目标` 的**祖先链**（带环检测，最多 512 层）；
2. 数据文件（`RegHive`、`RegPaths.dat`）只从**目标层**拷；
3. `CleanBoxFolders()` 清空 `drive/user/share`；
4. **对链上每一层**（从根到叶）依次：
   - `ApplyLayerDeletions`：解析该层 `FilePaths.dat`，把标记为删除的路径删掉；
   - `CopyLayerFolder`：`QDirIterator::Subdirectories` 递归覆盖拷贝；
5. 最后 `ini.setValue("Current/Snapshot", ID)` + `sync()`。

### 6.3 `FilePaths.dat` 的格式（自己逆出来的）

`Sandboxie/core/dll/file_del.c` 写入（`:408-430`）/读取（`:742`）：

```
UTF-16LE 文本，每行：path|HEXFLAGS[|relocation]\r\n
```

- `path` 是箱内相对路径，形如 `\drive\C\Apps\foo\data`；
- `FILE_DELETED_FLAG = 0x0001`、`FILE_RELOCATION_FLAG = 0x0002`；
- **flags 是十六进制**（`QString::toInt(&ok, 16)`，用十进制解析会得到 0 然后静默什么都不删）。

### 6.4 崩溃：`CleanBoxFolders` 是异步的

第一版改成同步物化后，点「恢复快照」直接 `EXCEPTION_ACCESS_VIOLATION`，读地址 `0x18`（空指针成员偏移），
`ExceptionAddress = QSbieAPI.dll+0x2578e` → 符号化后是 `CSbieProgress::IsFinished+0x3b`，调用者是 `CSandMan::AddAsyncOp`。

根因：`CleanBoxFolders` 内部是 `QtConcurrent::run(...)` 并返回 `SB_PROGRESS(OP_ASYNC, pProgress)`；
我用 `SB_STATUS Status = CleanBoxFolders(...)` 接住，进度对象被丢弃但状态仍是 `OP_ASYNC`，
`SnapshotsWindow::HandleResult` 见到 `OP_ASYNC` 就 `AddAsyncOp(Status.GetValue())` → `pProgress` 为空 → `pProgress->IsFinished()` 崩。
（顺带还有逻辑竞态：清空还没做完就开始拷。）

修法两步：

1. `SelectSnapshot` 改成只做校验 + 建 `CSbieProgress` + `QtConcurrent::run(SelectSnapshotAsync, pProgress, BoxPath, ID)` + 返回 `SB_PROGRESS(OP_ASYNC, pProgress)`；
   worker 里用**值拷贝**参数，不碰 `CSandBox` 成员，结束时 `pProgress->Finish(SB_OK)`。
2. `CSandMan::AddAsyncOp` 开头加防御：`if (pProgress.isNull()) return SB_ERR(...)`。

> 崩溃转储分析方法（没装 WinDbg 也能查）：`pip install minidump` 读 `exception_records[0].ExceptionRecord`，
> 线程 `ContextObject` 按 x64 CONTEXT 偏移取 `RIP=0xF8 / RSP=0x98 / RBP=0xA0`；
> 再用 ctypes 调 dbghelp（`SymInitialize` + `SymLoadModuleExW` + `SymFromAddrW` + `SymGetLineFromAddr64`）。
> **坑**：`SYMBOL_INFOW.SizeOfStruct` 必须设成 **88**，否则 `SymFromAddr` 返回 err 87。

## 7. Rust 侧：`sbie-box`（CLI + MCP）

### 7.1 为什么写 Rust

内核与 UI 只能 C++（驱动是 minifilter + 注入，换语言等于从零造沙箱）；但 CLI/自动化这一层用 Rust 干净：
单文件、无 Qt 运行库、`cargo build --release` 即得 500KB 左右的绿色 exe。

### 7.2 最大的坑：`C:\Windows\Sandboxie.ini` 普通权限写不进去

- 直接 `Add-Content` → `Access to the path 'C:\Windows\Sandboxie.ini' is denied.`
- **`SbieIni.exe` 可以写**，因为它走 `SbieDll_UpdateConf` → 服务 `SbieIniServer`（SYSTEM 身份落盘），
  并且写完后会 `SaveIni()` + `SbieApi_ReloadConf()`，**立即让驱动重载，不用重启 SandMan**。

所以 Rust 侧的「写」全部包成 `SbieIni.exe` 调用：

```
SbieIni.exe set|append|insert|delete <section> <setting> [value]
```

语义细节（都实测过）：

- `set <sec> <key> <value>` 是**整体替换**该 key（多值会被压成一行）；
- `set <sec> <key>`（无 value）= 删这个 key；
- `append <sec> <key> <value>` 追加值行，**key 不存在会自动建**，section 不存在也会自动建；
- `set <sec> "*"`（无 value）= **删整节**（`sbieiniserver.cpp:1078-1082` 的特例）；`delete` 只能删某个值行，删不了节。
- **`SbieIni.exe` 的分词器不支持引号**（`apps/ini/cmd.c:47-89` 自己实现 `CmdEatString/CmdCopyString`），
  所以从 CLI 写 `RunCommand=名字|"C:\a b\x.exe"` 是写不进去的。

### 7.3 路径含空格怎么办：8.3 短名

C++（SandMan）侧写 `RunCommand` **可以**带引号（走 `SbieIniSet` 直接落 ini，不经命令行分词器）；
Rust CLI 走 `SbieIni.exe`，只能避开空格 —— 用 8.3 短名：

```powershell
(New-Object -ComObject Scripting.FileSystemObject).GetFile('<path>').ShortPath
```

> `cmd` 的 `for %A in (...) do @echo %~sA` 在本机这套 shell 下会被吞掉，输出变成 `D:\"D:\..."`，别用。

### 7.4 箱根路径：别忘了 `\Sandbox` 这一层

`Sandboxie/core/drv/box.c:271-315 Box_InitPaths` 的优先级：

1. 箱级 `FileRootPath` → 直接用；
2. 否则箱级 `BoxRootFolder`，此时后缀是 `\Sandbox\<箱名>`；
3. 否则默认 `\??\%SystemDrive%\Sandbox\%USER%\%SANDBOX%`。

**全局 `[GlobalSettings] BoxRootFolder` 不是驱动用的路径来源，只有箱级才生效**（`Conf_Get` 的全局回退是另一回事）。
这个 bug 让我们 `sbie-box status` 一直报箱子不存在 —— 修法是：`FileRootPath` 优先，否则 `BoxRootFolder`（箱级，回落全局）
`trim_end_matches('\\')` 后 `.join("Sandbox").join(箱名)`。

### 7.5 其它 Rust 小坑

- `box` 是 Rust 保留字 → 所有标识符改名 `box_name`；批量正则替换时容易把字符串字面量（帮助文本、`sbie-box`）一起改坏，要事后逐条核对。
- PowerShell `Set-Content` 默认 ANSI，会把 UTF-8 源码写坏 → 用 `[System.IO.File]::WriteAllText($p,$s,(New-Object System.Text.UTF8Encoding($false)))`。
- `Start.exe /box:X /listpids` 会返回 `0`、`4`、`10` 之类系统进程号；过滤条件至少 `pid > 4`，否则 `terminate` 会死等。
- 空箱时 `/listpids` 也会输出裸 `0`，别把它当 PID。

## 8. 界面侧：三个原生菜单项

### 8.1 中文标签怎么进 C++ 源（不想动代码页）

源码全 ASCII，用 UTF-8 字节转义 + 一个小助手：

```cpp
static inline QString SbieView__L(const char* Utf8) { return QString::fromUtf8(Utf8); }
SbieView__L("\xe5\xaf\xbc\xe5\x85\xa5\xe6\x96\x87\xe4\xbb\xb6\xe5\xa4\xb9")   /* 导入文件夹 */
```

### 8.2 三处菜单的落点

- 主菜单 `Sandbox`：`m_pImportFolder` / `m_pImportProgram`（`CreateMenu()` 与 `CreateOldMenu()` **各一份**，两处都要加，否则"经典菜单"模式下看不到）；
- 箱右键 → `Box Content` 子菜单：`m_pMenuImportFolder` / `m_pMenuImportProgram`；
- 箱右键 → `Run` 子菜单：`m_pMenuRunCustom`（运行指定程序…），紧挨 `Run Program`；
- 另外 `NULL` 初始化、`setEnabled` 状态、`OnSandBoxAction()` 派发分支三处都要接上，少一处就是点了没反应。

> `SandMan/Views/SbieView.h` 是 **CRLF**、`SbieView.cpp` 是 **LF**，用脚本改的时候要注意，混用会让 diff 全红。

### 8.3 「导入」与「运行」共用一套路径判定

```cpp
// 有箱内副本就返回它，否则返回空
QString CSandBoxPlus::GetBoxedCopy(const QString& HostFile) {
    QString Path = QDir::toNativeSeparators(HostFile);
    if (Path.length() < 4 || Path.at(1) != ':') return QString();
    QString BoxFile = m_FilePath + "\\drive\\" + Path.left(1).toUpper() + "\\" + Path.mid(3);
    return QFile::exists(BoxFile) ? BoxFile : QString();
}
```

- 写入口用 `MakeBoxAwareCommand()`：有副本 → `%BoxRoot%\drive\…`（`MakeBoxCommand` 会把箱根替换成 `%BoxRoot%`）；
- 启动时用 `GetBoxAwareFullCommand()`：`GetFullCommand` 展开 `%BoxRoot%` → `GetCommandFile` 拆出「文件 + 参数」→
  有副本就把文件换成箱内路径（带引号）再拼回参数。**这样连以前写进 ini 的旧入口都自动受益。**

实测确认这条路可行：把 `notepad.exe` 拷进 `…\New_Box\drive\C\Windows\System32\`，用**箱内物理路径**启动 →
`Start.exe` 退出码 0、窗口标题 `[#] 无标题 - 记事本 [#]`、进程自报 `C:\Windows\system32\notepad.exe`（Sandboxie 做了正确映射）。

## 9. 本机 shell 的坑（不写下来一定会再犯）

1. **`ops_bash` 经 `niu.exe` 包装**：`cd`/`ls` 到某些目录（如 `.LoginBoxData`）会**静默空输出** → 改用 PowerShell 绝对路径。
2. **PowerShell 长命令里的 `$var` 会被 bash 吞**：凡是带 `$` 的脚本，必须写成 `.ps1` 再 `powershell -File` 跑。
3. **PowerShell 里 `$_` 同样被吞**（`$_.Name` 之类）→ 一律走 `.ps1`。
4. **`cmd //c "...bat"` 在本环境无效**（只打印横幅就退出）→ 用 `powershell -NoProfile -ExecutionPolicy Bypass -Command "cmd /c 'D:\...\x.cmd'"`。
5. **带中文的 `.ps1` 必须是 UTF-8 BOM**，否则 Windows PowerShell 5.1 按 ANSI 读，中文字符串比较全失败（`python` 写文件用 `encoding='utf-8-sig'`）。
6. **`param()` 默认值里的 `$PSCommandPath` / `$MyInvocation.MyCommand.Path` 在 `-File` 调用下为空** →
   报 `Split-Path : 无法将参数绑定到参数"Path"，因为该参数为空字符串`。改用 `$PSScriptRoot`（回调函数体内）或硬编码兜底。
7. **读弹窗文字**：标准 Windows 对话框（class `#32770`）用 `EnumWindows` + `EnumChildWindows` + `GetWindowTextW` 就能拿到全文；
   截图 + OCR 不可靠（会被前台窗口遮挡），且跨完整性级别（对方 elevated、我方非提权）时 `SetForegroundWindow` / `PrintWindow` 都会被 UIPI 挡掉。
8. **当前 shell 非管理员**（UAC 提示被禁用），`Start-Process -Verb RunAs` 直接 `Access is denied` → 需要提权的步骤只能交用户执行，脚本要写成「管理员运行 + 幂等 + 回读校验」。
